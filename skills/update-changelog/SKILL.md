# Обновление changelog

Используй этот скилл, когда пользователь просит обновить changelog, историю изменений или список изменений версии. Сначала прочитай соседний скилл plain-text-style. Его файл находится в ../plain-text-style/SKILL.md.

## Где обновлять

Найди существующий CHANGELOG.md или другой файл истории изменений. Проверь инструкции проекта и ссылки на отдельный репозиторий документации. Обновляй основной файл на месте. Не создавай дубликат рядом с кодом, если changelog вынесен в документацию.

Если файла ещё нет и место понятно из структуры проекта, создай его там. Если есть несколько разных журналов и нельзя определить нужный, уточни только место назначения. Явно названный пользователем файл имеет приоритет.

## На чём основывать запись

- Посмотри последнюю запись, отметку исходного коммита и теги версий, если они есть.
- Прочитай новые коммиты после последней записи. Учитывай незакоммиченные изменения через git status и git diff.
- Сопоставь сообщения коммитов с изменёнными файлами и текущим результатом. Сообщение коммита само по себе не подтверждает заявленное поведение.
- Учитывай историю разговора как источник контекста. Просьба пользователя что-то сделать ещё не означает, что работа выполнена.
- Включай завершённые и проверенные изменения. Не добавляй планы, незавершённые задачи, неподтверждённые результаты и обещания.
- Объединяй несколько коммитов об одной возможности в один понятный пункт. Не перечисляй каждый технический шаг и не повторяй уже описанные изменения.

Если точная граница предыдущего обновления неизвестна, используй явно указанный период или доступную историю. Не выбирай произвольные последние десять коммитов и не называй их полным релизом. При существенной неопределённости уточни период.

Завершённая локальная правка может попасть в запись. Не называй её опубликованной, выпущенной или доступной игрокам, пока это не подтверждено. Если со времени предыдущей записи ничего не изменилось, сообщи об этом и не создавай пустой раздел.

## Дата и версия

В начале каждой записи указывай версию и дату без времени. Если пользователь задал период, указывай обе даты. Используй дату завершения или публикации, если она известна. В остальных случаях используй текущую дату в часовом поясе пользователя.

Формат версии - V1.0. Это заглавная V, целое мажорное число, точка и целое минорное число. Не добавляй третье число. Следующие версии могут выглядеть как V1.1 и V2.0.

Бери версию из основного файла версии проекта или из прямого указания пользователя. Не увеличивай её только из-за обновления текста. Если версии ещё нет, начни с V1.0 и согласуй её с местом хранения версии в проекте. Если в проекте другой формат и нет указания его менять, уточни соответствие. Не переименовывай существующие теги и релизы ради оформления.

Новые версии ставь сверху. Для уже существующей версии дополняй её запись, сохраняя дату реального выпуска. Не создавай несколько одинаковых заголовков. Старые записи сохраняй, кроме явно запрошенных исправлений.

## Как писать

- Сначала описывай самое заметное изменение для игрока или пользователя. Мелкие исправления ставь ниже.
- Используй простой список без вложенности. Один пункт передаёт одно изменение или несколько тесно связанных изменений.
- Начинай пункт с одного подходящего эмодзи. После него пиши с заглавной буквы и заканчивай точкой.
- Кратко сообщай, что уже сделано и какой результат это даёт. Используй формулировки вроде "Добавили", "Изменили" и "Исправили".
- Соблюдай plain-text-style. Не добавляй жирный текст, курсив, скобочные уточнения, длинные тире и точку с запятой.
- Не копируй имена веток, хеши коммитов и внутренние названия методов в пункты для читателя, если без них понятен результат.
- Сохраняй точные числа и названия, если они помогают понять изменение. Не придумывай измерения, проценты и преимущества.

## Пример оформления

Этот пример показывает форму записи. Не переноси его факты в чужой проект.

### V1.0 - 24.10.2026

- 🚁 Добавили атаки с разных направлений. Дроны подлетают к базе издалека.
- 🏗️ Добавили улучшения зданий. Новые уровни открывают больше возможностей для базы.
- 🖱️ Упростили перемещение объектов. Теперь их можно перетаскивать мышкой.

Для периода подходит заголовок "V1.1 - 25.10.2026 - 31.10.2026". В самом CHANGELOG.md используй H1 для названия документа и H2 для записей версий.

## Проверка и результат

Проверь место назначения, дату, версию, порядок пунктов и подтверждение каждого факта. Убери повторы, планы и детали, которые не объясняют результат. Убедись, что формат списка совпадает с общим стилем.

Если проект хранит исходный коммит или период для следующего обновления, обнови эту отметку после проверки. Незакоммиченные изменения перечисли в служебной отметке отдельно, чтобы следующий запуск не потерял их и не выдал повторно.

Сохрани файл и кратко сообщи, какую запись обновил. Само обновление changelog не означает запрос на публикацию релиза, отправку сообщений, создание тега или push. Выполняй эти действия, если пользователь отдельно поручил их в текущей задаче.
